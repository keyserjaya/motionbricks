# MotionBricks Unity Runtime

Runs the [MotionBricks](https://github.com/NVlabs/motionbricks) SOMA motion generation model natively
in Unity and retargets the generated motion onto any VRM humanoid avatar. Works in the Editor and in
Windows standalone builds with no Python and no native plugins beyond the Unity Inference Engine.

- **Backend**: Unity Inference Engine (`com.unity.ai.inference`), GPU compute with automatic CPU
  fallback. One generation takes ~80 ms on the CPU backend and yields 0.6–1.9 s of motion.
- **Rig**: SOMA humanoid (30 predicted joints) mapped onto Unity humanoid bones, which covers VRM 0.x
  and VRM 1.0 avatars through UniVRM.
- **Verified**: the encode/decode/endpoint-correction pipeline is validated against golden fixtures
  generated by the reference TensorRT engine (`Tests/Fixtures`, 4/4 tests green).

## Install

1. Add the package to your project's `Packages/manifest.json`:

   ```json
   "com.nvlabs.motionbricks": "file:../path/to/motionbricks/unity/com.nvlabs.motionbricks"
   ```

2. Import the SOMA model. Copy `mmm_v6_soma_fp16.onnx` from the MotionBricks repository
   (`motionbricks/assets/onnx/soma/unity/`) anywhere under `Assets/` — the Unity Inference Engine
   imports it as a `ModelAsset` on drop.

   > Use the **unity/** subfolder of the ONNX assets: those files have the token-count path rewired
   > for the Unity Inference Engine (see `tools/unity_golden/simplify_token_output.py`). The
   > upstream model's integer shape subgraphs mis-evaluate in InferenceEngine and corrupt the
   > generated motion.

3. Add `SomaVrmRetargeter` to your avatar (any UniVRM avatar works — its Animator must hold a
   humanoid avatar) and drive it from `GeneratedSomaMotionPlayer`.

## Minimal usage

```csharp
var skeleton = SomaSkeleton.CreateDefault();
using var backend = new SomaInferenceEngineBackend(modelAsset);   // GPU, falls back to CPU
var player = new GeneratedSomaMotionPlayer(backend, skeleton);

player.SeedHistoryFromPose(seedPose);                             // one pose, e.g. a clip pose
retargeter.SetAnchor(avatarHips.position, seedPose[0].position);

player.Generate(targetPoses, skeleton.NumJoints,
    new TargetPoseInferenceParams(numPosesToUse: 4, transitionEarlyByFrames: 4));

// Per frame:
player.Sample(deltaTime, pose, footContacts);   // interpolated playback
retargeter.ApplyPose(pose);                     // drive the VRM avatar
player.RecordPose(deltaTime, pose);             // context for the next generation
if (player.TimeToTransition <= deltaTime)
{
    player.Generate(nextTargetPoses, skeleton.NumJoints, ...);  // chain
}
```

`targetPoses` are local joint transforms (`UnityEngine.Pose`, root first) at 30 Hz — sample them
from a `SomaClip` (BVH) with `SomaBvhLoader.LoadBvh`, place them with `SomaTargetPlacement`, and
scale their speed with `AdjustTargetPoseSpeed`.

## Notes

- **Coordinate space**: Unity's Y-up world *is* the SOMA model space, so no space conversion is
  applied (`model_to_runtime` is the identity). The Python demos convert to a Z-up world because
  their viewer is MuJoCo-based; that step is intentionally absent here.
- **GPU vs CPU backend**: on some InferenceEngine versions the GPU (compute shader) backend
  mis-executes this model's integer shape subgraphs and returns NaN token logits. The backend probes
  the GPU once and falls back to the CPU automatically (a warning is logged). The CPU backend is
  fast enough to generate from a background thread at transition points.
- **Animation Rigging**: `SomaVrmRetargeter` disables any `RigBuilder` on the avatar at startup —
  rig constraints overwrite the humanoid bones every frame and fight the generated motion. Re-enable
  it if you want constraints on top.
- **Fingers**: the model does not predict finger motion; hands keep the avatar's rest pose.
- **Neck**: SOMA has two neck joints (`Neck1`, `Neck2`); both map onto the VRM neck and head.
